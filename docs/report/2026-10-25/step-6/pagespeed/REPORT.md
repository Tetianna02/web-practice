# Швидкодія: спроби PSI та окремий локальний Lighthouse

Дата: 25.10.2026. URL: https://tetianna02.github.io/web-practice/. **Код, стилі, зображення та налаштування сайту не змінені.**

## PageSpeed Insights: результат недоступний

Для обох стратегій, **mobile і desktop**, виконано запити офіційного PSI API без ключа. В обох випадках отримано HTTP **429 RESOURCE_EXHAUSTED**:

```text
Quota exceeded for quota metric 'Queries' and limit 'Queries per day'
of service 'pagespeedonline.googleapis.com'
for consumer 'project_number:583797351490'.
```

Докази: [api-attempt.json](api-attempt.json), [mobile-api.json](mobile-api.json), [desktop-api.json](desktop-api.json). Це відповідь сервісу вимірювання; вона не означає помилку Home. Google дозволяє пробні API-запити без ключа, однак вони обмежені. [Документація API](https://developers.google.com/speed/docs/insights/v5/get-started).

В офіційному вебінтерфейсі було відкрито mobile-посилання, а потім перевірено звичайне введення адреси через Analyze. Після початку аналізу UI показав:

```text
Unable to resolve https://tetianna02.github.io/web-practice/.
Try checking the URL for validity.
```

Його службовий запит `/data/batchexecute` фактично повернув **429** із поясненням Google про автоматизовані запити комп'ютера або мережі. [web-ui-attempt.json](web-ui-attempt.json) зберігає цей статус і повідомлення, [web-ui-mobile.png](web-ui-mobile.png) — реальний екран помилки, [psi-initial.png](psi-initial.png) — першу спробу. Напис Unable to resolve у цих умовах не доводить, що DNS/адреса Home несправні: публічні браузерні перевірки та пряме завантаження 41 ресурсу успішні.

Після явного блокування подальших спроб обходу не було. JSON PSI зі справжніми оцінками й скриншотів успішних mobile/desktop PSI-звітів **немає**. Ключі, акаунти, платні сервіси чи VPN не створювалися. Вебінтерфейс не дійшов до звіту та вкладок пристроїв; окремої успішної desktop UI-перевірки не заявлено.

**Вимога саме про PSI поки не закрита.** Для неї потрібен ручний запуск власницею за [інструкцією](MANUAL_PSI.md). Це зовнішнє обмеження, а не дозвіл підмінити PSI іншими цифрами.

## Додаткова діагностика: локальний Lighthouse, не PSI

Оскільки PSI недоступний, окремо запущено Lighthouse CLI **13.5.0** на цій самій публічній HTTPS-адресі. Це локальні лабораторні результати, збережені для пояснення можливих проблем. Вони не є оцінками PageSpeed Insights і не підтверджують реальні Core Web Vitals.

| Показник | Mobile | Desktop |
|---|---|---|
| Performance | **87** | **100** |
| Accessibility | **92** | **96** |
| Best Practices | **100** | **100** |
| SEO | **100** | **100** |
| FCP — поява першого вмісту | 1,2 с | 0,3 с |
| LCP — найбільший видимий елемент | 2,5 с (2471,529 мс до округлення) | 0,7 с |
| TBT — сумарне блокування реакції під час завантаження | 420 мс (423 мс до округлення) | 40 мс |
| CLS — зсуви розмітки | 0,001 | 0 |
| Speed Index | 1,6 с | 0,7 с |

Запуски послідовні: mobile о 22:49:45, desktop о 22:50:37 за Києвом. У Lighthouse немає runtimeError чи runWarnings. Mobile: стандартна емуляція 412×823, DPR 1,75, CPU slowdown 4×, simulated throttling. Desktop: 1350×940, DPR 1, CPU 1×. Ручні функціональні Playwright-перевірки окремо виконані на 360 і 1440 px. Оцінки можуть змінюватися залежно від навантаження ПК, мережі, кешу та моменту перемикання слайдера; один запуск не гарантує майбутнього балу.

Повні звіти: [mobile HTML](local-lighthouse/mobile.report.html), [desktop HTML](local-lighthouse/desktop.report.html), відповідні `.report.json`; [summary.json](local-lighthouse/summary.json) містить обрані діагностики та налаштування. Реальні знімки локальних HTML-звітів: [mobile](local-lighthouse/mobile-summary.png), [desktop](local-lighthouse/desktop-summary.png). Їх не підписано як PSI.

Відтворення через Lighthouse CLI без встановлення залежностей у проєкт:

```text
npm exec --yes --package=lighthouse@13.5.0 -- lighthouse https://tetianna02.github.io/web-practice/ --chrome-flags="--headless" --only-categories=performance,accessibility,best-practices,seo --output=json --output=html --output-path=mobile --quiet
```

Для desktop додати `--preset=desktop` і змінити output-path. Chrome має бути встановлений; за потреби його шлях задається `CHROME_PATH`. Команда тут наведена для відтворення звіту, не для зміни сайту. npm-залежності збережені в системному кеші поза Git. Попередження npm про застарілу транзитивну OpenTelemetry-залежність належить інструменту, а не коду магазину; оновлення npm не виконувалося.

## Що знижує оцінки — простою мовою

1. **На телефоні браузер довго обчислює розташування елементів.** У mobile 2,6 с роботи головного потоку, з них приблизно 1,54 с — Style & Layout, тоді як виконання JS приблизно 0,17 с. TBT 423 мс безпосередньо впливає на Performance. Lighthouse також указав примусовий перерахунок розмітки в `main.js`: після зміни карток читається/задається позиція прокрутки; є додаткові читання геометрії стрічок. Отже, проблема ширша за «великий JS-файл». [Пояснення TBT](https://developer.chrome.com/docs/lighthouse/performance/lighthouse-total-blocking-time), [forced reflow](https://developer.chrome.com/docs/performance/insights/forced-reflow).
2. **Частина картинок важча за потрібне.** `promo-banner-jbl.png` має 1 525 351 байт — приблизно 1,53 МБ. Для всіх зображень Lighthouse оцінив можливу економію у 2099 KiB mobile / 1825 KiB desktop; це оцінка інструмента, не гарантована економія. Нижні lazy-картинки можуть завантажуватися наперед поблизу екрана. Великі файли витрачають мобільний трафік навіть за доброго desktop-балу. [Доставка зображень](https://developer.chrome.com/docs/performance/insights/image-delivery).
3. **Hero-зображенню не задано високого пріоритету.** Воно вже є в початковому HTML і не lazy, що добре; Lighthouse радить `fetchpriority="high"`. У цих запусках оцінена економія LCP саме від цієї підказки — 0 мс, тому приріст балу не обіцяємо. [Пріоритет LCP](https://developer.chrome.com/docs/performance/insights/lcp-discovery).
4. **Доступність — окрема оцінка.** Червоний `#db4444` на білому має виявлений контраст близько 4,26:1, нижче потрібних 4,5:1 для дрібного тексту; є й інші елементи в повних списках аудиту. На mobile п'ять крапок слайдера мають зону 10×10 px, що замало для пальця. Саме ці перевірки знизили Accessibility, а не Performance. [Робота з контрастом у Chrome](https://developer.chrome.com/docs/devtools/accessibility/contrast).
5. **Кеш і CSS — менший пріоритет для нашого коду.** Сервер Pages віддає `Cache-Control: max-age=600` (10 хв). Це заголовок сервера, правка CSS його не подовжить. Мініфікація CSS дасть орієнтовно лише 2 KiB економії передавання; CSS у head потрібний для коректного першого показу. Червоні підказки не означають, що кожна з них напряму віднімає бали: оцінку Performance визначають метрики. Діагностики можуть перекриватися; їхню «економію» не можна просто підсумувати.

## Пропозиції: що зміниться після окремого дозволу

Нижче **тільки пропозиції**, нічого з цього не реалізовано.

| Пріоритет | Можлива зміна | Що зміниться для користувача | Як перевірити / обмеження |
|---|---|---|---|
| 1 | Пакетно формувати картки та оновлювати фільтр один раз після побудови всіх списків; згрупувати читання геометрії стрічок перед змінами | Менше повторних перерахунків, швидша реакція під час завантаження/фільтрації; вигляд, порядок карток, 2 desktop-ряди та disabled-стрілки залишаються такими самими | Повторити всі сценарії стрічок, пошук, 0/1/8/11/100 карток, ширини 360–1440; порівняти TBT кількома послідовними вимірами |
| 2 | Підготувати WebP-копії великих банерів/новинок із **тих самих** наявних зображень, зберігши прозорі поля, пропорції та позиціонування | Менше трафіку; ті самі товари, композиція і текст. Можлива слабка зміна стиснення, яку треба показати на порівнянні | Оригінали зберегти, не підмінювати іншим JBL/PS5-експортом; візуальна перевірка на 360/768/1440, гострі краї/прозорість/contain |
| 3 | Додати `fetchpriority="high"` лише початковому hero; за результатом вимірів розглянути точковий preload критичного шрифту | Головне зображення може почати завантажуватися раніше; сімейства, ваги й розміри шрифтів не змінюються | Не давати високий пріоритет усім слайдам/шрифтам; перевірити Network і LCP, немає гарантованого приросту |
| 4 | Збільшити зони натискання крапок слайдера щонайменше до 24×24 px, залишивши видимий круг 10 px | Пальцем легше влучити; можлива зміна відстаней між крапками, бо нинішні зони надто щільні | Узгодити невелику зміну пагінації та порівняти desktop із макетом; клавіатура/слайдер мають працювати як раніше |
| 5 | Точково затемнити червоний дрібний текст/фон кнопок, окремо перевірити зелені написи та інші позначені пари | Текст стане читабельнішим; **відтінки реально зміняться**, тому потрібне погодження відхилення від макета | Обчислити всі пари, повторити Lighthouse accessibility; не міняти шрифти чи розміри |
| Пізніше | Окрема мініфікована CSS-копія зі збереженням читабельного вихідника | Невелике зменшення файлу, орієнтовно 2 KiB у цьому звіті; вигляд не має змінитися | Низька користь на цьому етапі; не додавати складний build лише заради цього |

Зміна хостингу, власного CDN, service worker чи серверних заголовків у цей етап не пропонується як обов'язкова. Папка `docs/report` не завантажується при перегляді Home й не є причиною її бала швидкодії.

Після будь-якого погодженого пакета покращень потрібні нові виміри й регресійні перевірки. Наперед обіцяти 100 mobile не можна. Офіційний PSI використовує лабораторний Lighthouse, але його середовище відрізняється від локального; польові дані залежать від достатньої кількості відвідувань за попередній період. [Як читати PSI](https://developers.google.com/speed/docs/insights/v5/about).
