## 4. Вибір функціоналу на 12 та бонус

1. **USER/ADMIN.** Покупець керує власним профілем, кошиком, замовленнями, обраним; адміністратор — каталогом і статусами замовлень. Сервер перевіряє роль та власника кожного захищеного ресурсу.
2. **Два повні CRUD.** Основна сутність — products, друга — categories. Зв'язок використовується в каталозі й формах товару; для обох є Create/Read/Update/Delete через UI та API.
3. **Завершене замовлення.** Товар → кошик → доставка → серверний перерахунок → транзакція БД → підтвердження → історія Account.

Усі три розширення погоджені. Якщо виникне ризик дедлайну, спершу скорочувати другу чергу сторінок і необов'язкові прикраси; не залишати заглушки замість обов'язкової авторизації, CRUD чи серверних обмежень. Зміну погодженого обсягу обговорювати з користувачкою.

Два дешеві кандидати на бонус: наявна sticky-шапка зі зміною вигляду та таймери акцій. Для таймера після підключення API використовувати спільний sale_ends_at, а не різний строк від першого відкриття в кожному браузері. Wishlist і пагінацію реалізувати як корисні функції після основного сценарію; не рахувати кожну бонусну функцію окремим балом.

```text
categories 1 ─── N products 1 ─── N product_images
users      1 ─── N auth_sessions
```

Обмеження: ціна/залишок не від'ємні, кількість додатна, email і slug унікальні, зовнішні ключі валідні. Гроші — точний NUMERIC, не наближений float. У JS/JSON зафіксувати єдине представлення сум без втрати точності.

Категорію з товарами не видаляти до перенесення товарів: 409 і зрозуміле пояснення. Новий товар без історії можна фізично видалити для демонстрації повного CRUD; товар у замовленнях деактивувати, зберігши історію. Транзакція оформлення перевіряє і блокує потрібні залишки, створює orders/order_items, зменшує залишки й очищає кошик атомарно. Сервер бере ціни й власника з БД/сесії, не довіряє сумі чи user_id з браузера.

Параметри запитів перевіряються: позитивні ID/кількість, допустимі поля сортування, верхня межа limit, довжина пошуку. SQL — параметризований; динамічне сортування — лише з дозволеного переліку.

### 5.4. bcrypt, сесії, ролі й секрети

- Паролі хешувати **bcrypt** через асинхронні hash/compare. Сіль генерує бібліотека. Початковий орієнтир cost 12; перевірити час на Render Free, обґрунтовано налаштувати без надмірного навантаження, не нижче 10.
- Для bcrypt контролювати **72 байти UTF-8**, а не 72 символи: довший пароль явно відхиляти зрозумілим повідомленням, не обрізати мовчки. Однакові правила в реєстрації та вході; мінімальна довжина — 8 символів, як у наявній формі.
- Паролі не зберігати відкрито, не логувати, не надсилати назад і не зберігати у браузерних сховищах. [Первинна документація bcrypt](https://github.com/kelektiv/node.bcrypt.js#security-issues-and-concerns).
- Власні серверні сесії: випадковий криптографічний токен; у БД лише token_hash, user_id, строк дії. SHA-256 придатний для хешування випадкового високoентропійного токена, але не використовується замість bcrypt для пароля.
- Для навчальної версії токен у sessionStorage та Authorization: Bearer. Орієнтир TTL — 8 годин, налаштовується сервером. Після оновлення сторінки профіль звіряється через /auth/me.
- Вихід анулює запис сесії та очищує токен: старий токен не має працювати. Прострочена сесія дає 401 і пропозицію увійти знову.
- sessionStorage доступний JavaScript: обмежити сторонні скрипти, не вставляти користувацькі тексти через innerHTML, перевірити XSS. JWT не потрібний для першої версії.
- USER створюється за замовчуванням; role із публічного register ігнорується. ADMIN створюється контрольованою серверною процедурою, не через публічну кнопку.
- Middleware перевіряє сесію, строк дії, роль і власника даних. Відсутність кнопки Admin у USER не є захистом API.
- Обмеження частоти для login/register/contact, обмеження розміру тіла запиту, HTTPS, без логування токенів.
- CORS — тільки погоджені frontend-origin та локальна розробка. Це не захист від Postman/curl і не заміна авторизації. [Express CORS](https://expressjs.com/en/resources/middleware/cors/).
- До PostgreSQL підключається серверний pg Pool через рекомендований Neon connection string/TLS. Малий пул, тайм-аути й обробка відновлення після сну; не створювати новий пул на кожний HTTP-запит.

| Змінна | Значення та секретність |
|---|---|
| DATABASE_URL | Секретний URL підключення до Neon PostgreSQL, лише backend |
| NODE_ENV | Середовище виконання |
| PORT | Порт, на Render задає платформа |
| FRONTEND_ORIGINS | Дозволені адреси клієнта |
| SESSION_TTL_HOURS | Строк сесії |
| BCRYPT_COST | Погоджена вартість хешування |
| ADMIN_EMAIL / ADMIN_INITIAL_PASSWORD | Лише тимчасова контрольована ініціалізація адміністратора; пароль потім змінити/прибрати змінну |

У Git лише .env.example з порожніми/безпечними демонстраційними значеннями. Реальний .env у .gitignore, секрети на Render у Environment. Адреса API у frontend публічна і не вважається секретом. Секрети не розміщувати у PNG, звіті, логах чи комітах.

## 6. Пріоритети сторінок і поведінка

Спочатку перша черга **в зазначеному порядку**: Home → Category → Product → Sign Up/Log In → Cart → Checkout → Account → Admin → 404. Потім друга черга: Wishlist → About → Contact. Sign Up та Log In — окремі сторінки, одна група пріоритету.

Порядок екранів визначає пріоритет верстки; робоча авторизація з'являється після backend, Admin — після серверних ролей. Ранні статичні форми не називати завершеною функцією. 404 включити до приймання основного обсягу, до другої черги.

| Черга / порядок | Сторінка | Потрібна функціональність |
|---|---|---|
| 1 / 1 | Home | Адаптивність, меню, слайдер, таймери, модальна форма; потім товари з API й правильні переходи |
| 1 / 2 | Category | Пошук, категорія, сортування, пагінація, loading/empty/error |
| 1 / 3 | Product | Дані за ID, галерея, ціна, залишок, кількість, кошик; обране після Wishlist |
| 1 / 4 | Sign Up / Log In | Окремі сторінки, серверна реєстрація/вхід, повідомлення помилок, повернення до запитаної дії |
| 1 / 5 | Cart | Вхід обов'язковий; зміна кількості, видалення, суми й наявність через API |
| 1 / 6 | Checkout | Дані доставки, оплата при отриманні, серверний підсумок, створення замовлення, номер/підтвердження |
| 1 / 7 | Account | Профіль, вихід, власна історія й деталі замовлень |
| 1 / 8 | Admin | Серверний захист; товари й категорії з повним CRUD; статуси замовлень |
| 1 / 9 | 404 | Зрозуміла помилка, Home/каталог, перевірка невідомої адреси та ресурсних шляхів |
| 2 / 1 | Wishlist | Обране акаунта в БД, видалення й перенесення до кошика |
| 2 / 2 | About | Український тематичний зміст за макетом, навігація |
| 2 / 3 | Contact | Демонстраційні контакти позначені чесно; форма з валідацією, записом у БД і повідомленням про результат |

Модальну форму на Home зберегти попри наявність окремих Sign Up/Log In: використати спільну логіку API/валідації. Не додавати зайвої окремої сторінки підтвердження, якщо вистачає стану Checkout.

## 7. Поетапне виконання

### Етап 1. Доведення Home та перша публікація

**Мета:** підготувати першу здачу головної, не розпорошуючись на backend і додаткові сторінки.

**Роботи після окремої команди:**

1. Переглянути поточні зміни Git без скидання чужої роботи; підготувати контрольну точку перед реалізацією.
2. Звірити Home з доступними локальними еталонами/specs. Якщо повного PNG Home немає, уточнити його наявність; Figma MCP не використовувати.
3. Довести секції, відступи, типографіку, зображення, контраст та стани кнопок. Перевірити кирилицю і доцільність локального підключення шрифтів.
4. Виправити маркери конфлікту _variables.css та узгодити його використання; не залишати зайвого непідключеного коду.
5. Зберегти/перевірити слайдер, меню, таймери, кнопку «Вгору», модальне вікно з формою, кнопку/фон/клавіатурне закриття й клієнтську валідацію.
6. Самостійно адаптувати mobile; перевірити 320–1440+ px та відсутність ненавмисного горизонтального скролу.
7. Вирішити заглушки відповідно до уточненого обсягу першої здачі: не створювати враження готової реєстрації/кошика. На Pages не збирати реальні дані, явно зазначити навчальну демонстрацію.
8. Перевірити HTML/CSS, Console/Network, локальні й зовнішні посилання; підготувати потрібні ресурси до Git.
9. Допомогти налаштувати Pages у наявному репозиторії, пояснювати кроки. Перевірити публічний URL, шляхи /web-practice/, favicon і ресурси; зробити PageSpeed mobile/desktop.
10. Зберегти докази першої здачі. Нагадати про PNG решти макетів перед етапом 2.

**Рішення користувачки:** точний дедлайн і вимоги викладача до першої здачі; наявний PNG Home; необхідний доступ до GitHub. Не просити пароль або секрет у чаті.

**Приймання:** Home доступна за URL, візуально звірена з доступним еталоном, адаптивна, модальна форма правильно перевіряє дані, немає необроблених помилок і ненавмисних 404, збережені результати перевірок. Backend не є умовою цього етапу, якщо викладач його не вимагає.

**Залежність:** затверджений план та окрема команда «Починай етап 1». Зараз ця команда ще не надана.

### Етап 2. Основні сторінки за пріоритетом

**Передумова-нагадування: користувачка експортує з Figma PNG решти сторінок перед початком етапу. Мобільних макетів немає, їх не вимагати.**

**Мета/роботи:** погоджено перенести frontend до окремої папки, оновити публікацію; спільні шапка/футер, компоненти; верстати Category, Product, Sign Up/Log In, Cart, Checkout, Account, оболонку Admin та 404 у погодженому порядку. Підготувати форми та loading/empty/error-стани з демонстраційними даними; визначити контракт API. Wishlist/About/Contact залишити на другу чергу, до цього не робити битих навігаційних посилань.

**Рішення користувачки:** PNG та зміст неоднозначних елементів макета; уточнення від викладача.

**Приймання:** переходи між створеними сторінками, прямі URL, семантика, заголовки/метатеги, форми, адаптивність, HTML/CSS, консоль. Статичні оболонки не видаються за функціональний backend.

**Залежність:** етап 1 та PNG основних екранів.

### Етап 3. Express та PostgreSQL на Neon Free

**Мета/роботи:** повторно перевірити безкоштовні умови; створити Neon Free та Render Free без платних опцій; таблиці/міграції/seed; підключення pg через TLS; публічне читання каталогу; серверна валідація, status codes, обробка помилок; перше розгортання API на Render. Авторизаційні/CRUD-записи не відкривати публічно до захисту етапу 5.

**Рішення користувачки:** необхідний вхід у хмарні кабінети й вибір доступного регіону; бюджет уже визначений — 0.

**Приймання:** міграції відтворюють схему, зв'язок category/product використовується, API працює з розгорнутою БД, неправильні дані не приймаються, секрети лише на сервері. Перевірити ліміти й відновлення після бездіяльності.

**Залежність:** контракт і структура даних з етапу 2.

### Етап 4. Каталог через API

**Мета/роботи:** прибрати статичні масиви як основне джерело даних; підключити Home, Category, Product через fetch до Render API; пошук/категорія/сортування/пагінація; коректні loading/empty/error/retry; не маскувати збій API непомітним поверненням демонстраційних даних.

**Рішення користувачки:** конкретні доступні фільтри й кількість товарів на сторінці; за замовчуванням простий достатній набір без надлишкових налаштувань.

**Приймання:** дані реально приходять із БД через API; 0/1/багато товарів, невідомий ID, повільне/недоступне API, помилкові параметри, зміни каталогу.

**Залежність:** етапи 2–3.

### Етап 5. Авторизація та USER/ADMIN

**Мета/роботи:** bcrypt, register/login/logout, серверні сесії, /auth/me, профіль Account, USER за замовчуванням, контрольоване створення ADMIN, middleware ролей/власника, rate limit.

**Рішення користувачки:** безпечні демонстраційні акаунти; поля профілю, якщо є відмінності від макета. Не використовувати особисті паролі або реальні персональні дані для демонстрації.

**Приймання:** правильний/неправильний пароль, дубль email, bcrypt-ліміт 72 байти, logout анулює токен, сесія переживає оновлення сторінки до строку дії, 401/403, неможливо передати собі ADMIN чи прочитати чужі дані.

**Залежність:** етапи 3–4.

### Етап 6. Admin і два повні CRUD

**Мета/роботи:** UI й API товарів та категорій; створення/перегляд/редагування/видалення; серверна валідація; підтвердження видалення; готові зображення з ресурсів; правила видалення пов'язаних записів.

**Рішення користувачки:** лише неоднозначні поля макета; завантаження фото вже відкладене, вибір наявних ресурсів погоджений.

**Приймання:** два повні CRUD-цикли через UI та API, зміни відображаються в каталозі, недійсні дані відхиляються, прямі запити USER/гостя заборонені.

**Залежність:** етап 5 та оболонка Admin з етапу 2.

### Етап 7. Основний сценарій покупки

**Мета/роботи:** кошик акаунта в БД; кількість/видалення/суми; Checkout із доставкою та оплатою при отриманні; серверний перерахунок, перевірка залишків, транзакція, захист повторного запиту; підтвердження; історія Account і статуси в Admin. Завершити основну чергу та перевірку 404 до другої черги.

**Рішення користувачки:** точні варіанти доставки/поля адреси, якщо макет неоднозначний. Реальний платіжний шлюз не додавати.

**Приймання:** товар → кошик → замовлення → Account; ціну не можна підмінити, подвійне натискання не створює дубль, залишки не стають від'ємними, чужі замовлення недоступні, збій не залишає половину замовлення в БД.

**Залежність:** етапи 4–6.

### Етап 7Б. Друга черга: Wishlist, About, Contact

**Мета/роботи у цьому порядку:** Wishlist зі станом акаунта в БД і кнопками обраного на товарах; About за PNG; Contact із записом звернень, валідацією й rate limit; довести дешеві бонусні функції.

**Рішення користувачки:** тексти About, демонстраційні контакти та PNG відповідних екранів. Нестачу часу обговорити до зміни обсягу.

**Залежність:** завершена основна черга та етап 7.

### Етап 8. Повне тестування і фінальна публікація

**Мета/роботи:** Render Static Site для фінального клієнта, Render API + Neon; HTTPS/CORS/адреси, усі ролі й сторінки, крайні випадки, браузери, адаптивність, валідатори, PageSpeed; перевірка секретів і читабельності коду; на Pages лишається статична навчальна демонстрація.

**Рішення користувачки:** підтвердити доступ до Safari/iPhone/Mac або чесно зафіксувати непроведену перевірку; остаточні URL.

**Приймання:** закриті обов'язкові вимоги, немає заглушок основних сценаріїв, працюють frontend/API/БД після бездіяльності, збережені докази з датою й версією коду. Платних сервісів немає.

### Етап 9. Звіт і репетиція захисту

**Рішення користувачки:** шаблон звіту, точна дата захисту, правило бонусного бала.

**Приймання:** звіт відповідає фактичному стану, кожна вимога має доказ, у звіті немає секретів; користувачка може пройти демонстрацію й пояснити frontend → API → БД.

Обов'язкова матриця:

- [W3C HTML](https://validator.w3.org/): кожний HTML-файл; додатково сформований динамічний DOM. Помилки нашого коду виправити, результати включити у звіт.
- [Jigsaw CSS](https://jigsaw.w3.org/css-validator/): підключені стилі; відрізняти помилки від попереджень про сучасні можливості.
- [PageSpeed Insights](https://pagespeed.web.dev/): усі публічні сторінки, mobile/desktop, реальний URL товару. Для авторизованих Account/Admin та вмісту Cart/Checkout/Wishlist додатково Lighthouse локально після входу: PSI не передає нашу сесію й не оцінить закритий вміст. Зафіксувати це обмеження, не видавати тест login-екрана за тест адмінки.
- PDF не встановлює мінімального бала PSI. Робоча ціль для статичних сторінок Performance 90+, але це орієнтир, не гарантія й не вимога викладача.
- Console/Network: без необроблених помилок, відсутніх ресурсів, CORS і mixed content; API-помилки обробляються інтерфейсом.
- Ширини 320, 375/390, 480, 768, 1024, 1440+ px та проміжні; без ненавмисного горизонтального скролу сторінки. Навмисна горизонтальна стрічка товарів не дорівнює поламаному макету.
- Актуальні Chrome, Firefox, Edge, Safari. Доступ до справжнього Safari ще уточнити; WebKit-емуляцію не називати повною перевіркою Safari.
- Клавіатура, focus-visible, labels/type, Escape/кнопка/фон модального вікна, повернення фокуса, повідомлення помилок, prefers-reduced-motion.
- Довгі назви/слова, відсутні/великі зображення, 0/1/багато товарів/позицій.
- Усі посилання, ресурси, phone/email, прямі URL; навмисний тест невідомої адреси відокремити від ненавмисних 404.
- API-тести мають перевіряти справжні правила: валідацію, ролі, власника, CRUD, транзакцію/повтор запиту. Не писати зайві тести, що лише повторюють реалізацію стилів.

Матеріали звіту: мета/предметна область, сторінки, макет та адаптивні відхилення, технології з обґрунтуванням, структура, ER-схема/ключі/зв'язки, API, bcrypt/сесії/ролі, два CRUD, сценарій покупки, desktop/mobile і стани помилок, W3C/Jigsaw/PSI, браузерна матриця, негативні тести й виправлення, адреси frontend/API/Git, дата/версія, висновки та відомі обмеження. Не включати паролі, токени, секретні URL БД чи реальні особисті дані.

У PDF немає шаблону, обсягу й правил оформлення звіту; користувачка надасть окремий шаблон наприкінці. Структуру документа підлаштувати під нього, не втрачати зібрані докази.

## 10. Відкриті уточнення та порядок продовження

Не потребують зупинення збереження плану, але мають бути уточнені до відповідного етапу:

1. Точні дати першої здачі/захисту та вимоги до першої здачі — користувачка запитає викладача.
2. Повний локальний еталон Home — звірити на початку етапу 1, якщо його досі немає.
3. PNG інших сторінок — користувачка експортує **до етапу 2**; нагадати після етапу 1.
4. Доступ до Safari — відповідь не визначена, уточнити до браузерного приймання.
5. Шаблон звіту — користувачка надасть наприкінці; докази накопичувати раніше.
6. Правило бонусного бала/оцінки понад 12 — користувачка уточнить у викладача.

План уже затверджений. Після його збереження **нічого більше не реалізовувати**. Наступна дія лише після повідомлення користувачки **«Починай етап 1»**.
